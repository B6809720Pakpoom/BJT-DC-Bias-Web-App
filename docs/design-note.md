# Design Note — BJT DC Bias Web App

## บริบท

Lab 02 (ENG29 2121) ต้องการให้สร้างเว็บแอปที่ **คำนวณจริงด้วย Python backend** สำหรับ DC operating point
ของวงจร BJT Common-Emitter แบบ voltage-divider bias พร้อม validation และ warning เมื่อผลอยู่นอก
forward-active region ข้อจำกัดคือเวลา lab จำกัดและต้องใช้ไลบรารีมาตรฐานเป็นหลัก

## การตัดสินใจหลัก

### 1. แยก `dc_bias.py` ออกจาก `app.py`

`dc_bias.py` เป็นฟังก์ชันบริสุทธิ์ (pure function) ที่รับ/คืนค่า SI units (V, Ω, A) ไม่ import Flask
ไม่รู้จัก HTTP หรือ HTML เลย

**เหตุผล:** สมการเป็นส่วนที่ต้องตรวจสอบให้ถูกต้องที่สุด และต้องทดสอบได้โดยไม่ต้องมี web server
เมื่อ logic ไม่ปนกับ I/O เทสต์จึงอ่านง่าย (เทียบตัวเลขโดยตรง) และ debug ได้เร็ว

**ผลที่ตามมา:** ถ้าจะเปลี่ยน UI เป็น CLI หรือ API ก็ไม่ต้องแตะสมการ

### 2. UI รับหน่วย kΩ แต่ backend รับ Ω

ผู้ใช้กรอกตัวต้านทานเป็น kΩ (ตรงกับใบงานและค่าที่ใช้จริงในแล็บ) แต่ `dc_bias.py` รับ Ω เท่านั้น
การคูณ 1000 เกิดขึ้นที่ `app.py` ใน `parse_form()` ที่เดียว

**เหตุผล:** ป้องกันปัญหาหน่วยปนกัน (unit confusion) ซึ่งเป็น bug ที่พบบ่อยที่สุดในงานคำนวณ
การมีจุดแปลงจุดเดียวทำให้ค้นหา/ตรวจสอบได้ง่าย และเทมเพลตแสดงค่า Ω ที่แปลงแล้วใต้ช่องกรอก
เพื่อให้ผู้ใช้เห็นว่าค่าที่ถูกนำไปคำนวณคืออะไร

**ทางเลือกที่ปฏิเสธ:** ให้ `calculate_dc_bias()` รับ kΩ แล้วคูณเอง — ทำให้ฟังก์ชันผูกกับ UI
และถ้าวันหลังมีคนเรียกจาก script ด้วย Ω จะได้ผลผิดเงียบ ๆ

### 3. Route เดียว: `GET /` และ `POST /`

`GET` แสดงฟอร์มพร้อมค่าเริ่มต้น, `POST` คำนวณแล้ว render หน้าเดิมพร้อมผลลัพธ์

**เหตุผล:** ไม่ต้องมี state ฝั่ง server, ไม่ต้องมี JavaScript, กด refresh แล้วคำนวณซ้ำได้
และตรงกับข้อกำหนดของใบงานที่ให้ผลลัพธ์อยู่หน้าเดียวกับฟอร์ม

**ทางเลือกที่ปฏิเสธ:** แยก `/calculate` แล้ว redirect — เพิ่มความซับซ้อนโดยไม่ได้อะไร
และทำให้ค่าที่กรอกหายไปหลัง redirect

### 4. เกณฑ์ region: cutoff ก่อน แล้วค่อย saturation

```
ถ้า VTH <= VBE            → cutoff   (IB = IC = IE = 0, VC = VCC, VE = 0)
ไม่งั้นถ้า VCE <= 0.3 V    → saturation (มี warning, ค่า VCE ไม่น่าเชื่อถือ)
ไม่งั้น                     → active
```

**เหตุผล:** ใช้ `if` แล้ว `elif` เพื่อให้ผลลัพธ์มีสถานะเดียวเสมอ ไม่มีทางติดสองป้ายพร้อมกัน
และตรวจ cutoff ก่อนเพราะถ้า VTH ≤ VBE สมการ IB จะให้ค่าติดลบหรือศูนย์ ซึ่งไม่มีความหมายทางกายภาพ
(ที่ VTH = VBE พอดี ใช้ `<=` เพื่อให้จัดเป็น cutoff ไม่ใช่ active ที่ IB = 0)

**ทางเลือกที่ปฏิเสธ:** คำนวณทุกอย่างแล้วค่อย clamp — จะได้ IB ติดลบปนเข้าไปในผลลัพธ์และ warning
ที่สับสน

### 5. ไม่คำนวณฝั่ง JavaScript

การคำนวณทั้งหมดอยู่ที่ Python backend

**เหตุผล:** ใบงานกำหนดให้ใช้ Python คำนวณ และการมีสูตรเดียวในที่เดียวทำให้ผลตรงกับเทสต์
ถ้าคำนวณสองฝั่งจะต้อง sync สูตรและมีโอกาสไม่ตรงกัน

### 6. ทดสอบด้วย `unittest` จาก stdlib

**เหตุผล:** เป็นข้อจำกัดของงาน (dependency เดียวที่อนุญาตคือ Flask) และ `unittest` เพียงพอ
สำหรับ 21 เทสต์ ทั้งระดับสมการและ HTTP (ผ่าน `app.test_client()` ซึ่งไม่ต้องเปิด port จริง)

### 7. ไม่ปัดค่ากลาง

เก็บ float เต็มความละเอียดตลอดสาย แล้วปัดเฉพาะตอนแสดงผล (V 3 ตำแหน่ง, mA/µA 3 ตำแหน่ง, kΩ 2 ตำแหน่ง)

**เหตุผล:** การปัดกลางทางทำให้ error สะสม และทำให้เทสต์เทียบค่าอ้างอิงไม่ตรง

### 8. ภาษาใน UI

ข้อความอธิบาย/error เป็นภาษาไทย แต่ศัพท์เทคนิคคงเป็นอังกฤษ (cutoff, saturation, forward-active, VCE)

**เหตุผล:** ผู้อ่านเป็นนักศึกษาไทย และศัพท์เทคนิคแปลไทยแล้วกำกวมกว่าต้นฉบับ

## โครงสร้างไฟล์

| ไฟล์ | ความรับผิดชอบ | ห้ามทำ |
|---|---|---|
| `dc_bias.py` | สมการ + validation + region | ห้าม import Flask, ห้ามรู้จักหน่วย kΩ |
| `app.py` | Flask routes, แปลงหน่วย, จัดการ error | ห้ามใส่สมการ |
| `templates/index.html` | การนำเสนอ | ห้ามคำนวณ |
| `static/style.css` | layout/สี | — |
| `tests/` | พิสูจน์พฤติกรรม | ห้ามผูกกับ markup ที่ไม่จำเป็น |

## ข้อจำกัดที่ยอมรับ

- แบบจำลอง forward-active ใช้ β คงที่และ VBE คงที่ จึงไม่แม่นเมื่อกระแสเปลี่ยนมาก
  หรืออุณหภูมิเปลี่ยน
- ไม่มี Early effect (ไม่คิด `ro`) จึงไม่เหมาะงานที่ต้องการความแม่นระดับออกแบบจริง
- Saturation เป็นเพียงการเตือน ไม่ได้แก้สมการใหม่ให้ถูกต้องตาม region นั้น
