# Design Note — BJT DC Bias Web App

## บริบท

Lab 02 (ENG29 2121) ต้องการให้สร้างเว็บแอปที่ **คำนวณจริงด้วย Python backend** สำหรับ DC operating point
ของวงจร BJT Common-Emitter แบบ voltage-divider bias พร้อม validation และ warning เมื่อผลอยู่นอก
forward-active region Lab 03 ต่อยอดเว็บเดิมให้เลือกได้ 3 โหมด (divider/fixed/emitter) โดยผล divider
เดิมต้องคงเดิม ข้อจำกัดคือเวลา lab จำกัดและต้องใช้ไลบรารีมาตรฐานเป็นหลัก

## การตัดสินใจหลัก

### 1. แยก `dc_bias.py` ออกจาก `app.py`

`dc_bias.py` เป็นฟังก์ชันบริสุทธิ์ (pure function) ที่รับ/คืนค่า SI units (V, Ω, A) ไม่ import Flask
ไม่รู้จัก HTTP หรือ HTML เลย

**เหตุผล:** สมการเป็นส่วนที่ต้องตรวจสอบให้ถูกต้องที่สุด และต้องทดสอบได้โดยไม่ต้องมี web server
เมื่อ logic ไม่ปนกับ I/O เทสต์จึงอ่านง่าย (เทียบตัวเลขโดยตรง) และ debug ได้เร็ว

**ผลที่ตามมา:** ถ้าจะเปลี่ยน UI เป็น CLI หรือ API ก็ไม่ต้องแตะสมการ

### 2. UI รับหน่วย kΩ แต่ backend รับ Ω

ผู้ใช้กรอกตัวต้านทานเป็น kΩ (ตรงกับใบงานและค่าที่ใช้จริงในแล็บ) แต่ `dc_bias.py` รับ Ω เท่านั้น
การคูณ 1000 เกิดขึ้นที่ `app.py` ใน `parse_form()` ที่เดียว

**เหตุผล:** ป้องกันปัญหาหน่วยปนกัน (unit confusion) ซึ่งเป็น bug ที่พบบ่อยที่สุดในงานคำนวณ
การมีจุดแปลงจุดเดียวทำให้ค้นหา/ตรวจสอบได้ง่าย และเทมเพลตแสดงค่า Ω ที่แปลงแล้วใต้ช่องกรอก
เพื่อให้ผู้ใช้เห็นว่าค่าที่ถูกนำไปคำนวณคืออะไร

**ทางเลือกที่ปฏิเสธ:** ให้ `calculate_dc_bias()` รับ kΩ แล้วคูณเอง — ทำให้ฟังก์ชันผูกกับ UI
และถ้าวันหลังมีคนเรียกจาก script ด้วย Ω จะได้ผลผิดเงียบ ๆ

### 3. Route เดียว: `GET /` และ `POST /`

`GET` แสดงฟอร์มพร้อมค่าเริ่มต้น, `POST` คำนวณแล้ว render หน้าเดิมพร้อมผลลัพธ์

**เหตุผล:** ไม่ต้องมี state ฝั่ง server, กด refresh แล้วคำนวณซ้ำได้
และตรงกับข้อกำหนดของใบงานที่ให้ผลลัพธ์อยู่หน้าเดียวกับฟอร์ม
(ใน Lab 03 มี JavaScript เพียงไม่กี่บรรทัดเพื่อซ่อน/โชว์ช่องตามโหมด ไม่ได้คำนวณหรือแปลงหน่วย — ดูข้อ 5)

**ทางเลือกที่ปฏิเสธ:** แยก `/calculate` แล้ว redirect — เพิ่มความซับซ้อนโดยไม่ได้อะไร
และทำให้ค่าที่กรอกหายไปหลัง redirect

### 4. เกณฑ์ region: cutoff ก่อน แล้วค่อย saturation

```
ถ้า VTH <= VBE            → cutoff   (IB = IC = IE = 0, VC = VCC, VE = 0)
ไม่งั้นถ้า VCE <= 0.3 V    → saturation (มี warning, ค่า VCE ไม่น่าเชื่อถือ)
ไม่งั้น                     → active
```

**เหตุผล:** ใช้ `if` แล้ว `elif` เพื่อให้ผลลัพธ์มีสถานะเดียวเสมอ ไม่มีทางติดสองป้ายพร้อมกัน
และตรวจ cutoff ก่อนเพราะถ้า VTH ≤ VBE สมการ IB จะให้ค่าติดลบหรือศูนย์ ซึ่งไม่มีความหมายทางกายภาพ
(ที่ VTH = VBE พอดี ใช้ `<=` เพื่อให้จัดเป็น cutoff ไม่ใช่ active ที่ IB = 0)

**ทางเลือกที่ปฏิเสธ:** คำนวณทุกอย่างแล้วค่อย clamp — จะได้ IB ติดลบปนเข้าไปในผลลัพธ์และ warning
ที่สับสน

### 5. ไม่คำนวณฝั่ง JavaScript

การคำนวณทั้งหมดอยู่ที่ Python backend

**เหตุผล:** ใบงานกำหนดให้ใช้ Python คำนวณ และการมีสูตรเดียวในที่เดียวทำให้ผลตรงกับเทสต์
ถ้าคำนวณสองฝั่งจะต้อง sync สูตรและมีโอกาสไม่ตรงกัน

ใน Lab 03 อนุญาตให้ JS ใน `templates/index.html` ทำหน้าที่เดียวคืออ่านค่า `<select name="mode">`
แล้วตั้ง `hidden` บน `.field[data-modes]` เท่านั้น (ฟังก์ชัน `sync()`) — ไม่มีสมการ ไม่มีการคูณ 1000
และไม่ได้เป็นแหล่งของค่าที่ส่งเข้า `dc_bias.py`

### 6. ทดสอบด้วย `unittest` จาก stdlib

**เหตุผล:** เป็นข้อจำกัดของงาน (dependency เดียวที่อนุญาตคือ Flask) และ `unittest` เพียงพอ
สำหรับ 21 เทสต์ ทั้งระดับสมการและ HTTP (ผ่าน `app.test_client()` ซึ่งไม่ต้องเปิด port จริง)

### 7. ไม่ปัดค่ากลาง

เก็บ float เต็มความละเอียดตลอดสาย แล้วปัดเฉพาะตอนแสดงผล (V 3 ตำแหน่ง, mA/µA 3 ตำแหน่ง, kΩ 2 ตำแหน่ง)

**เหตุผล:** การปัดกลางทางทำให้ error สะสม และทำให้เทสต์เทียบค่าอ้างอิงไม่ตรง

### 8. ภาษาใน UI

ข้อความอธิบาย/error เป็นภาษาไทย แต่ศัพท์เทคนิคคงเป็นอังกฤษ (cutoff, saturation, forward-active, VCE)

**เหตุผล:** ผู้อ่านเป็นนักศึกษาไทย และศัพท์เทคนิคแปลไทยแล้วกำกวมกว่าต้นฉบับ

## โครงสร้างไฟล์

| ไฟล์ | ความรับผิดชอบ | ห้ามทำ |

## ข้อจำกัดที่ยอมรับ

- แบบจำลอง forward-active ใช้ β คงที่และ VBE คงที่ จึงไม่แม่นเมื่อกระแสเปลี่ยนมาก
  หรืออุณหภูมิเปลี่ยน
- ไม่มี Early effect (ไม่คิด `ro`) จึงไม่เหมาะงานที่ต้องการความแม่นระดับออกแบบจริง
- Saturation เป็นเพียงการเตือน ไม่ได้แก้สมการใหม่ให้ถูกต้องตาม region นั้น

## Lab 03 — การตัดสินใจเพิ่มเติม

### 9. แยกฟังก์ชันตามวงจร แต่ใช้โครงสร้างผลลัพธ์ร่วมกัน

เพิ่ม `calculate_fixed_bias()` และ `calculate_emitter_bias()` ใน `dc_bias.py` โดย **ไม่แตะ**
`calculate_dc_bias()` เดิม (คงพฤติกรรม Lab 2 ทุกประการ รวม VTH/RTH และเกณฑ์ cutoff/saturation)

ทั้งสามฟังก์ชันคืน `DcBiasResult` ตัวเดียวกัน มี `as_dict()` ที่ใช้ชื่อคีย์/หน่วยตรงกัน
(`vb_v`, `ve_v`, `vc_v`, `vce_v`, `ic_ma`, `ib_ua`, `region`, `warnings`) ส่วน `vth`/`rth`
เป็น `None` ในโหมดใหม่เพื่อไม่ให้แสดงตัวเลขปลอม

**เหตุผล:** ตารางเปรียบเทียบ A1–A5 ต้องอ่านค่าต่างโหมดด้วยคีย์เดียวกัน และการไม่แก้ฟังก์ชันเดิม
ทำให้พิสูจน์ "Divider ได้ผลเดิม" ได้ด้วยเทสต์ชุดเดิม 33 ตัวที่ผ่านอยู่แล้ว

**ทางเลือกที่ปฏิเสธ:** เขียนฟังก์ชันเดียวรับ `mode` แล้วใส่ `if` ข้างในสมการ — จะทำให้
`dc_bias.py` รู้จัก UI และยากต่อการตรวจสมการแยกกรณี

### 10. เลือกโมเดลด้วยตารางใน `app.py`

```
MODE_FIELDS  = {โหมด → ชื่อฟิลด์ที่อนุญาต}
CALCULATORS  = {โหมด → ฟังก์ชันใน dc_bias.py}
```

route ตรวจ `mode` ก่อน: ถ้าไม่อยู่ในตาราง → แจ้ง `โหมดไม่รู้จัก` ทันที (ห้าม fallback เป็น Divider)
จากนั้น `parse_form()` อ่านเฉพาะฟิลด์ของโหมดนั้น → แปลง kΩ→Ω ที่จุดเดียว → เรียก `CALCULATORS[mode]`

**เหตุผล:** ใบงานข้อ 04.4 ต้องการ `if`/`elif` เลือกตามค่าที่ส่งจากฟอร์ม การใช้ตารางคู่กับ
`if mode not in MODE_FIELDS` ทำให้เพิ่มโหมดใหม่ได้โดยไม่แก้โครง route และป้องกันกรณี
"Fixed Bias แล้วระบบบังคับกรอก R1/R2" หรือ "โหมดผิดแล้วเงียบ ๆ ไปคำนวณ Divider"

### 11. ไม่โชว์ผลเก่าตอน error

ตอน `ValueError` เรียก `render_template("index.html", …, errors=[…])` **โดยไม่ส่ง** `result`
และ `display` ทำให้ Jinja ข้าม `<section class="results">` ทั้งหมด

**เหตุผล:** A5 ต้องการให้เห็นชัดว่าผลที่แสดงเป็นของข้อมูลรอบนี้ ถ้าส่ง `result` เก่ามาด้วย
ผู้ใช้จะเข้าใจผิดว่า RB=0 ยังคำนวณได้ (นี่คือจุดที่ใบงาน Section 06 เตือน)

### 12. สคริปต์อิสระแยกจากโปรแกรมที่ตรวจ

`tools/independent_reference.py` ใช้ `decimal.Decimal` 50 หลัก ตั้ง `IE` เป็นตัวตั้ง (ต่างเส้นทางจาก
`dc_bias.py` ที่ตั้ง `IB`) และ **ไม่ import** `dc_bias`/`app` ค่าที่ได้จึงใช้เป็นคำตอบอ้างอิงได้
ตามที่ใบงาน Section 06 กำหนด

### 13. วิธีตรวจผลจริง: Playwright MCP = NOT RUN → OpenCode Browser

ตรวจสภาพจริงแล้ว: ไม่มี `node`/`npx`, ไม่มี `opencode.json`/`.jsonc`, ไม่มี MCP `playwright`
ใน session นี้ จึงบันทึก `NOT RUN` พร้อมเหตุผลใน `docs/validation.md` และใช้ `tools.browser.*`
ของ OpenCode Desktop แทนตามที่ใบงาน Section 05 อนุญาต (ให้คะแนนการตรวจผลเท่ากัน)

และภาพหน้าเว็บ `docs/evidence/A2-fixed-bias.png` — ไม่ได้ใช้การอ่านโค้ดหรือ `curl` แทน browser

### 14. เกณฑ์ saturation margin
