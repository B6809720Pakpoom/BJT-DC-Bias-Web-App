# Reflection — BJT DC Bias Web App

## สิ่งที่ได้เรียนรู้

### 1. ตัวต้านทานสองตัวแทนด้วย Thevenin ได้ ทำให้สมการเหลือชั้นเดียว

ก่อนทำ lab นี้ ผมมองวงจร voltage-divider ว่ามีสมการหลายชั้น (หา VB ก่อน แล้วค่อยหา IB)
พอแปลง R1 ‖ R2 เป็น VTH กับ RTH แล้ว เขียน KVL ของลูป base–emitter ได้สมการเดียว:

```
IB = (VTH − VBE) / (RTH + (β + 1)·RE)
```

ทุกค่าที่เหลือต่อจาก IB ได้เลย ทำให้ทั้งโปรแกรมมีสมการจริงอยู่บรรทัดเดียว
และเข้าใจได้ว่าทำไม R2 ถึงต้องเล็กพอที่จะทำให้ VTH สูงกว่า VBE

### 2. "ค่า IB ติดลบ" ไม่ใช่ค่าที่ผิดการคำนวณ แต่ผิดสมมติฐาน

ตอนแรกผมคิดว่าจะ clamp IB ให้เป็นศูนย์เมื่อติดลบ แต่พบว่าปัญหาคือ **สมมติฐานว่า transistor ทำงาน
ใน forward-active ไม่จริงตั้งแต่ต้น** การตรวจ `VTH ≤ VBE` ก่อนแล้วคืนค่า cutoff ทั้งชุด
สะอาดกว่าการไปแก้ตัวเลขที่ได้จากสมการที่ใช้ไม่ได้แล้ว

### 3. หน่วยเป็นแหล่ง bug ที่เงียบที่สุด

กรอก 100 (kΩ) แต่ backend รับ Ω ถ้าลืมคูณ 1000 ผลจะผิด 1000 เท่าโดยไม่มี error ใด ๆ
การบังคับให้แปลงที่จุดเดียวและแสดงค่า Ω ให้ผู้เห็น ช่วยลดความเสี่ยงนี้ได้มาก

### 4. TDD จับ "ขอบ" ที่ผมไม่ได้คิดถึง

เทสต์กรณี `VTH = VBE` พอดี (สร้าง R1 = 16142.857 Ω) ทำให้ต้องตัดสินใจว่าใช้ `<` หรือ `<=`
ผลลัพธ์ที่ถูกคือ cutoff จึงต้องเป็น `<=` — ถ้าไม่ได้เขียนเทสต์ก่อน ผมคงเขียน `<` ตามสัญชาตญาณ
แล้วปล่อยให้ IB = 0 ถูกจัดเป็น active

### 5. ทดสอบ HTTP ได้โดยไม่ต้องเปิด server

`app.test_client()` ทำให้เทสต์ route เร็วมาก (ทั้ง 21 เทสต์ใช้เวลา < 0.1 วินาที)
และรันใน CI ได้โดยไม่ต้องจัดการ port

## AI ช่วยอะไร / ไม่ช่วยอะไร

**ช่วยได้ดี:**
- ร่างโครงไฟล์ เทสต์ และเอกสารซ้ำ ๆ (boilerplate)
- แปลงสมการเป็นโค้ดที่อ่านง่าย และจัดรูปแบบตามสไตล์เดียวกันทั้งโปรเจกต์
- ไล่หากรณีขอบ (ศูนย์, ติดลบ, คอมมาเป็นจุดทศนิยม, ค่ามากผิดปกติ)
- คำนวณค่าอ้างอิงด้วยความละเอียดสูงเพื่อใช้ตรวจสอบ

**ยังต้องตัดสินใจเอง:**
- เลือกเกณฑ์ว่า VCE เท่าไรจึงเรียกว่า saturation (0.3 V) — เป็นการตัดสินใจเชิงวิศวกรรม
- เลือกว่าจะให้ UI รับ kΩ หรือ Ω — ขึ้นกับผู้ใช้และใบงาน
- ตรวจว่า warning ที่เขียนสื่อความหมายถูกต้องทางไฟฟ้า ไม่ใช่แค่ทำงานได้
- ยืนยันผลกับความเข้าใจวงจรจริง (AI อาจคำนวณถูกแต่ตีความ region ผิด)

**ข้อควรระวัง:** โค้ดที่ AI เขียนดูน่าเชื่อถือเสมอ ถ้าไม่มีเทสต์เทียบค่าอิสระ ก็ไม่มีทางรู้ว่าผิด
การที่ผมคำนวณมือและเขียนสคริปต์ Decimal แยกเส้นทาง (ใช้ IE เป็นตัวตั้งแทน IB) คือส่วนที่ทำให้
มั่นใจได้จริงว่าตัวเลขถูก ไม่ใช่แค่ "รันผ่าน"

## ข้อจำกัดของแบบจำลอง

1. **β คงที่** — ของจริง β เปลี่ยนตาม IC และอุณหภูมิ ผลจึงคลาดเคลื่อนเมื่อกระแสเปลี่ยนมาก
2. **VBE คงที่ 0.70 V** — ของจริง ~0.6–0.7 V และลดลงเมื่ออุณหภูมิสูงขึ้น
3. **ไม่มี Early effect** — ไม่คิด output resistance `ro` จึงไม่เห็นผลของ VCE ต่อ IC
4. **Saturation เป็นแค่ warning** — ไม่ได้แก้สมการเป็น `VCE = VCE(sat)` และคำนวณ IC ใหม่
   ค่า IC/VCE ที่แสดงในโหมดนี้จึงใช้ไม่ได้
5. **ไม่มีการจำลองอุณหภูมิหรือ tolerance ของอุปกรณ์**

## สิ่งที่จะทำต่อ

- เพิ่มโหมดคำนวณ saturation อย่างถูกต้อง (สมมติ VCE(sat) แล้วหา IC จากฝั่ง collector)
- เพิ่มกราฟ load line และจุด Q เพื่อให้เห็นภาพว่า operating point อยู่ตรงไหน
- รองรับการเลือกค่า E12/E24 ที่ใกล้ที่สุด เพื่อให้ตรงกับของจริงในห้องแล็บ
- เพิ่มการบันทึกผลหลายชุดเพื่อเปรียบเทียบ (เช่น เปลี่ยน RC แล้วดู VCE)
- เขียนเทสต์เปรียบเทียบกับผล ngspice สำหรับวงจรเดียวกัน
